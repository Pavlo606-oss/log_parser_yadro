# Парсер логов

Реализация микросервиса на Go, который принимает файлы-логи, парсит их и агрегирует информацию, сохраняет полученные данные в PostgreSQL и предоставляет REST-API для получения информации о сущностях.

## 🚀 Возможности

- Парсинг файлов `.db_csv` и `.sharp_an_info`.
- Сохранение данных о логах, узлах, портах и коммутаторах в PostgreSQL.
- Получение топологии по `log_id`.
- Получение информации об узле по `node_id`.
- Получение списка портов узла по `node_id`.
- Получение метаданных лога по `log_id`.
- Применение SQL-миграций для инициализации базы данных.
- Запуск проекта через Docker и Docker Compose.

## 🔧 Основные компоненты

### cmd/server — точка входа в приложение, запуск HTTP-сервера и инициализация зависимостей.

### internal/config — загрузка и хранение конфигурации приложения.

### internal/handler — HTTP-обработчики и вспомогательные структуры для API.

### internal/service — бизнес-логика приложения, связывает handler, parser и repository.

### internal/parser — парсинг входных файлов db_csv и sharp_an_info в структуры Go.

### internal/repository — работа с PostgreSQL: сохранение и чтение логов, узлов, портов, switch-данных и node info.

### migrations — SQL-миграции для создания и отката структуры базы данных.

### data — входные файлы логов для обработки.

### Dockerfile и docker-compose.yml — контейнеризация приложения и запуск вместе с PostgreSQL.

### Функциональные требования

#### 1. Доступ к файлу осуществляется через монтированную папку в самом проекте, название папки должно быть data/

##### Результат: выполнено 
##### Описание: папка data лежит в корне проекта, в ней уже лежат файлы логов из ТЗ.

#### 2. Разбить файлы на секции и собрать информацию по уникальным идентификаторам в объекты. Не все объекты могут быть полными, при любой ошибке отклонить файл и выкинуть ошибку

##### Результат: выполнено
##### Описание: Пакет parser содержит файл models.go, где описаны структуры, в которые собирается информация. Тут сложнее было определиться с определением ошибки. Так как в требованиях написано про неполноту, но ничего не написано про избыток, я решил считать лог битым только если не хватает информации. 

##### В файлах `.db_csv` сначала указаны имена параметров, а в следующей строке — их значения. Если значений меньше чем имён, тогда я выкидываю ошибку, также файл разбит на секции с помощью статусов парсинга (чтобы понимать когда нужно считывать параметры узлов, портов и т.д.)

##### В файлах `.sharp_an_info` есть фактически два неявных статуса(они не объявлены): процесс чтения и чтение завершено. Пока мы не встретим пустую строку, чтение будет идти, как только мы её встретим, программа проверяет наличие всех необходимых параметров. Если хоть одного нет, тогда лог считается битым и выкидывается ошибка.

#### 3. На основе nodes и ports построить граф. Будет плюсом если подумать какие связи могли бы быть, записать в Readme

##### Результат: выполнено
##### Описание: На основе таблиц `nodes` и `ports` проект позволяет построить граф топологии сети. Вершины графа соответствуют сетевым узлам (`nodes`), а порты (`ports`) выступают связями и интерфейсами узлов. В базовом варианте граф отражает структуру `Node -> Port` внутри одного лога. 
##### Для текущей модели данных могут быть следующие типы связей:

- `logs -> nodes` — связь **один ко многим**: один лог содержит множество узлов.
- `logs -> ports` — связь **один ко многим**: один лог содержит множество портов.
- `nodes -> ports` — связь **один ко многим**: один узел имеет несколько портов, каждый порт принадлежит одному узлу.
- `nodes -> nodes_info` — связь **один к одному** (фактически один к нулю или одному): у узла может быть одна запись с дополнительной информацией.
- `nodes -> switches` — связь **один к одному** (один к нулю или одному): для узлов хранится одна запись с параметрами коммутатора.

#### 4. Таблицы (минимум): logs, nodes, ports, nodes_info. Все связи реализованы через FK.Также необходим скрипт создания баз данных либо же наличие миграций. Они должны применяться автоматический при сборке

##### Результат: выполнено
##### Описание: созданы таблицы: `logs`, `nodes`, `ports`, `switches`, `nodes_info`, `sharp_an_info`. Как и было написано, все связи реализованы через FK. Скрипты создания и удаления таблиц лежат в папке `migrations`. Скрипт создания автоматически применяется при сборке, также все результаты парсингов записываются в базу данных и сохраняются между запусками приложения. Кроме того, в `Makefile` есть таргеты для создания и удаления таблиц, очистки данных PostgreSQL, хранящихся в именованном Docker volume `postgres_data`, что позволяет полностью сбросить состояние базы данных.

#### 5. POST /api/v1/parse/ – возвращает log_id. В тело передать путь до архива с логом. GET /api/v1/topology/{log_id} – возвращает список узлов и групп топологии. GET /api/v1/node/{node_id} – детали узла системы из лога. GET /api/v1/port/{node_id} –получение портов узла системы из лога. GET /api/v1/log/{log_id} – мета-информация о логе (status, количество узлов/портов,дата загрузки)

##### Результат: выполнено
##### Описание:
1. Для POST /api/v1/parse/ я использовал два URL : `/api/v1/parse` (потому что это уже выглядит как эндпоинт) и `/api/v1/parse/` (потому что так написано в ТЗ, я решил ему тоже соответствовать). В качестве тела запроса нужно передать лишь имя файла в переменной с именем `path`. Далее в таблицу `logs` добавляется запись лога, и относительно `id` лога заполняются уже другие таблицы.
2. GET /api/v1/topology/{log_id}. В URL запроса необходимо передать `id` лога, относительно которого возвращается информация с помощью связи, описанной в пункте 3. Возвращаются все узлы лога, и для каждого узла возвращается свой список соответствующих портов.
3. GET /api/v1/node/{node_id}. В URL запроса необходимо передать `id` узла, возвращается вся информация из таблиц `nodes`, `nodes_info`, `switches` для соответствующего узла.
4. GET/api/v1/port/{node_id}. В URL необходимо передать `id` узла, возвращается вся информация портов для соответствующего узла.
5. GET /api/v1/log/{log_id}. В URL необходимо передать `id` лога, возвращаются все необходимые метаданные для соответствующего лога.

Все модели JSON‑сообщений описаны в пакете repository. Только для POST /api/v1/parse/ модели запроса и ответа описаны в пакете handler.
Хотелось бы отметить, что в некоторых функциях узлов используются типы данных из пакета `database/sql`. Это обусловлено тем, что у узлов может и не быть коммутаторов, портов и т.д. (в таком случае они вообще не будут выведены из-за опции `omitempty`), а значение NULL считать как-то нужно. Также в пакете `repository` описан интерфейс `DBTX`, чтобы использовать транзакции и в случае битого лога сделать ROLLBACK.
